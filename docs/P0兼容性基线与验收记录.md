日期：2026-10-25。对应 [原引擎最小改造实施计划](原引擎最小改造实施计划.md) 的 P0。状态：已完成验收，下一阶段为 P1。

本阶段固定原引擎契约、差异和后续验收输入，不实现新的循环调度或恢复路径。生产 Java 代码、原 DSL DTO、Python 基线均未修改。

## 1. 原节点执行能力清单

通过只扫描 `engine/node/` 的 Spring 测试上下文核实原 NodeExecutor 注册，外部客户端使用替身，不启动数据库、Redis 或模型调用。

| Java 执行器 | nodeId 类型前缀 | 主要参数与行为 |
| --- | --- | --- |
| StartNodeExecutor | node-start | 接收运行输入，先写入变量池；原展示回调随后清空返回结果的 outputs |
| EndNodeExecutor | node-end | outputMode、template、reasoningTemplate；业务输出 content、reasoning_content；展示回调改写返回结果 |
| MockNodeExecutor | mock | delayMs、jitterMs、failureRate、payloadBytes、eventCount、eventBytes；输出 output、actualDelayMs、payload |
| LLMNodeExecutor | spark-llm | modelId、domain、template、systemTemplate、enableChatHistoryV2；使用原 outputs 定义命名文本，支持 reason 字段 |
| PluginNodeExecutor | plugin | 原 nodeParam 原样传给 PluginServiceClient；特殊 pluginId 由客户端选择 TTS，其他使用工具集成 |
| KnowledgeBaseNodeExecutor | knowledge-base | query 输入；repoId、docIds、namespace、topN、score、maxContextChars；输出 context、sources、results |

确认注册数量为 6。IF_ELSE、DECISION_MAKING、CODE、ITERATION 等虽然出现在 NodeTypeEnum 中，不能据此视为存在执行器。P0 未为这些类型补写业务实现。

证据：[LegacyDslBaselineTest.componentScanRegistersSixConcreteExecutorsAndNoConditionalExecutor][dsl-test]；原节点行为见 [LegacyNodeBaselineTest][node-test]。

## 2. 原 DSL 端到端字段映射

| 原数据 | Java 接收位置 | 已核实行为 |
| --- | --- | --- |
| flowId、uuid | WorkflowDSL | flowId 是定义标识；旧控制器将请求 chatId 写入 uuid |
| nodes[].id | Node.id | 原 getNodeType 从 `::` 之前的前缀识别类型 |
| nodes[].data.nodeMeta | NodeData.nodeMeta | 保留 nodeType、aliasName |
| data.inputs[].id/name | InputItem | 条件引用使用输入 ID，执行器传参使用输入 name；两者不能混淆 |
| schema.value.type/content | Value | ref 使用 content.nodeId/name；其他 type 当前走字面量分支 |
| data.nodeParam.cases | NodeData 的 Map | 数组与条件字段可原样保存，无须增加新 DTO 协议 |

数据库加载路径为 `WorkflowService.parseWorkflowDSL()`：提取保存 JSON 的 data 字段，再使用 Fastjson2 解析 WorkflowDSL。HTTP DTO 测试使用 Jackson 解析相同的原 JSON。10 份固定样例都可被两者读取，字段值语义保持一致。

一个实际差异：`nodeParam.score = 0.5` 经 Fastjson2 得到 BigDecimal，经 Jackson 得到 Double。P1/P2 的数值处理必须按数值语义归一，不能依赖运行时类完全相等或直接强转 Integer。测试单独锁定此差异，没有用字符串比较掩盖它。

证据：[LegacyDslBaselineTest.originalFixturesRoundTripThroughTheServiceAndHttpDtoFormats][dsl-test]、`serviceAndHttpParsingKeepJsonNumbersButUseDifferentDecimalClasses`。测试数据与当前、后续预期见 [原 DSL 样例目录][fixtures]。

## 3. 条件分支协议：现状与后续契约

### 3.1 已有配置约定

前端 IF_ELSE 节点使用 nodeParam.cases：

```json
{
  "id": "branch_one_of::pass",
  "level": 1,
  "logicalOperator": "and",
  "conditions": [
    {
      "id": "condition-pass",
      "leftVarIndex": "input-actual",
      "rightVarIndex": "input-expected",
      "compareOperator": "eq"
    }
  ]
}
```

leftVarIndex、rightVarIndex 指向 data.inputs 的 id，再通过该输入的 schema.value 解析值，不能直接当作变量名或输出名。

已核实的界面约定：

- 前端按 cases 数组展示 IF、ELSE IF，最后一项展示 ELSE。
- 新业务分支插入默认项之前，出口 ID 形如 branch_one_of::UUID。
- level 是优先级展示字段，默认项常为 999；数组位置是当前展示顺序依据。
- logicalOperator 使用 and/or。
- empty、not_empty、null、not_null 为单目操作，不能要求运行时解析无用的右值。

源码依据：[IF_ELSE 编辑器][frontend-branch]、[出口与输入 ID 初始化][frontend-utils]、[操作符列表][frontend-operators]。

Java 当前没有 IF_ELSE 执行器，也没有可据以承诺的 Java 分支数值转换和缺失值判断行为。旧 WorkflowEngine 会在执行器校验时拒绝它，即使图是无环的。normal_one_of / intent_chain 仅表示当前已经实现的成功／异常分流，不等于业务条件分支。

证据：[LegacyDslBaselineTest.conditionalCasesKeepTheirInputIdsOrderDefaultAndSourceHandles][dsl-test]、`anEnumEntryDoesNotMakeAnIfElseWorkflowExecutable`。两项测试分别证明字段保留及当前执行缺口。

### 3.2 P2 将实现的明确语义

以下是为后续实施确定的契约，不是 P0 已实现或已验证的运行能力。它不冒充 Python 版本或其他平台的既有求值行为。

1. 按 cases 数组顺序求值，首个匹配项生效，不额外按 level 重排。
2. 最后一项是默认出口；非默认项必须含有效条件。条件未满足属于正常路由，不返回节点失败。
3. and/or 短路求值，单目操作不解析右输入。未知逻辑符、未知操作符或出口配置错误明确拒绝。
4. 无业务分支匹配时选默认出口；没有有效默认出口则报告路由错误。
5. 不自动将字符串 "1"、"true" 转为数值或布尔。旧分支执行行为不存在，这些是新 Java 实现需要固定的规则。
6. 引用字段不存在或输入绑定无效时先报输入错误；显式 literal null 可用于 null 判断。P1 应保留“缺失”与“显式 null”的内部信息。旧入口现有的 null 透传不在 P0 改变。

全部 16 个前端操作符的实施口径：

| 操作符 | 后续求值口径 |
| --- | --- |
| contains / not_contains | 字符串子串；数组按元素同类型值相等判断，不隐式字符串化对象 |
| empty / not_empty | 字符串长度或列表/对象大小为零；空格字符串不自动 trim；null 使用专用操作符 |
| is / is_not | 布尔值判断，不将非空字符串当 true |
| start_with / end_with | 字符串前后缀，区分大小写 |
| eq / ne | 同类型值相等；Number 家族按十进制数值比较，1 与 1.0 相等 |
| gt / ge / lt / le | 仅 Number 家族，统一数值比较；不做字符串字典序比较 |
| null / not_null | 已成功解析的值是否为显式 null |

不支持的类型组合报条件类型错误，不能静默转为 false 然后进入默认分支。数组元素与对象的结构相等范围在 P2 用测试固定；若真实旧样例要求不同语义，应先记录差异再调整，不直接扩充新 DSL。

## 4. 重试、超时与错误策略

| 项目 | 原行为与证据 | 后续处理 |
| --- | --- | --- |
| maxRetries | 额外重试次数：0/1/2 对应最多 1/2/3 次调用 | 保留原单位，不改成 V2 的 maxAttempts 入参 |
| shouldRetry=false | 不使用额外重试额度，但正数 timeout 仍有效 | 保留 |
| 没有 retryConfig | 在调用线程直接执行一次，无该层超时控制 | 保留旧路径；增强预算另管 |
| timeout | Float 秒，转换毫秒；原代码以大于 0.001 秒为启用条件 | 不把原值当毫秒 |
| retryInterval | Float 秒，非正或缺省不等待 | 保留单位 |
| retryStrategy | 0 固定；1 乘当前失败尝试数；2 指数退避；未知值走固定 | 先保留，再明确配置校验差异 |
| Node.executedCount | 同一个 Node 对象再次 execute 时会累计，影响重试额度 | P1 使用独立激活视图；故障恢复不能无限重置同一激活额度 |
| 错误策略 0 或缺省中断 | ERR_INTERUPT，旧引擎抛异常，END 不执行 | 不等同可恢复暂停 |
| 错误策略 1 | 写入 customOutput，节点状态 ERROR，但走正常边 | 保留 |
| 错误策略 2 | ERR_FAIL_CONDITION，选择异常边 | 保留 |

证据：[LegacyRetryBaselineTest][retry-test] 测试实际基类重试循环与超时；固定、线性、指数及未知策略使用最小等待下界验证，没有依赖精确耗时或上界。错误策略通过实际 MockNodeExecutor 与原引擎执行，而非只测试自制结果对象。

原引擎还存在对 ERR_RETRY 状态再次调用执行器的外层循环；公共层的重试与调度层业务回跳需要分开，P1/P2 不应叠加默认重试。

## 5. 输入与变量池边界

| 输入或操作 | 当前结果 |
| --- | --- |
| Integer、Boolean、UUID | 保留原值类型 |
| 普通对象/Map、List | 转为 JSONObject / JSONArray 后保存 |
| result.items[1].text | 支持沿对象与数组索引读取 |
| items[0].text | 支持读取数组中的对象成员 |
| items[0] | 当前被当作完整字段名，返回 null，不代表取到数组元素 |
| 节点或直接字段不存在 | 返回 null |
| 路径中间字段不存在 | 可能抛 NullPointerException |
| 将字符串继续当对象取字段 | 抛 ClassCastException |
| 非数字数组索引或越界 | NumberFormatException / IndexOutOfBoundsException |
| pool.set(..., null) | 抛 NullPointerException |
| 某个输出字段本次没有写入 | 上一次该字段继续存在 |
| pool.get(nodeId) | 返回活动映射，调用方可修改 |
| 两个 VariablePool 实例 | 数据隔离，当前字段本身并非静态全局池 |

原 AbstractNodeExecutor 对缺失的直接引用会保留该输入名并透传 null；原 PluginNodeExecutor 确实会收到这个 null。输出写入则跳过 null，可能留下原值。P0 记录这些行为与缺陷，不在本阶段顺便修复。

证据：[LegacyVariablePoolBaselineTest][variable-test]、[LegacyNodeBaselineTest.missingReferenceIsPassedToTheOriginalPluginAsAnExplicitNullInput][node-test]。

P1/P2 需要有意处理：固定输入、私有视图、整份输出替换及明确的缺失输入行为。强化后的行为与旧接口不同之处必须在兼容矩阵中保留，不能宣称所有边界完全不变。

## 6. 业务结果与 SSE 展示结果

实际回调会修改原 NodeRunResult，而不是只格式化一份副本：

- START：业务输入已写入变量池，回调将返回结果 outputs 改为空 Map。
- END：业务 content、reasoning_content 已写入变量池，回调提取 nodeAnswerContent/ReasoningContent，随后把 outputs 换成 inputs，并清空 inputs。
- 因而直接把 execute() 返回值当作完整持久化业务结果，会丢失或改变输出。

P1 必须在公共层分离业务结果与展示副本。原 EndNodeExecutor 的渲染逻辑和输出字段应复用，不能改成 V2 的输入直接透传。

顺序链路的原流事件名统一为 stream，载荷为 LLMGenerate；不是文档注释中列出的独立 node_start/node_end 事件名。实测轨迹是：

```text
flow_obj / alias=flow_start
node-start::s 开始、结束
mock::work 开始、结束
node-end::e 开始、结束
flow_obj / alias=flow_end
finished：等待队列处理结束
```

结束内容来自旧模板，完整字段由实际载荷决定。发生中断时会先产生 interrupt 数据，仍产生旧工作流结束帧、刷新队列，随后引擎抛出异常；不能只看最后帧判断业务成功。

证据：[LegacyNodeBaselineTest][node-test]、[LegacyDslBaselineTest.originalStartMockAndEndExecuteWithOrderedStreamFrames][dsl-test]、`interruptionFlushesItsFramesBeforeTheEngineThrows`，以及原有 WorkflowMsgCallbackTest / SseStreamCallbackTest。

旧控制器遇到加载错误时不调用引擎，但仍关闭 SSE 写入线程；执行成功与执行异常均关闭连接资源。连接断开关闭消费者，不会取消已经排队的旧工作流任务。现有过载入口返回 503，已有测试覆盖消费者资源回收。

实验证据：[LegacyControllerBaselineTest][controller-test]、原 SseControllerOverloadTest、WorkflowMsgCallbackTest、SseStreamCallbackTest。测试区分“回调/写入线程结束”与“整个工作流取消”。

原应用默认启动 WorkflowApplication，扫描包含 V2 配置的包，`workflow.v2.enabled` 缺省启用；关闭该开关只关闭实验 V2，旧请求仍走旧引擎。独立 WorkflowV2Application 只装配其 V2 范围。P0 不改变默认开关，也不把新计划解释为已发生默认路径切换。

P1 起一次运行应固定实现标识；P4 保存它与定义版本，恢复时不根据当前默认配置换引擎。增强路径校验不通过时明确报错，不能悄悄回退旧路径。

## 8. 首批图结构的判定约定

这是一份 P2 能力校验器的输入，不表示 P0 已编写校验器。

| 结构 | 首批增强路径 | 判定依据 |
| --- | --- | --- |
| 单链路 | 支持 | 每次激活至多产生一个后继 |
| IF_ELSE 不同出口 | 支持 | 每次只选一个出口，每个出口至多一个目标 |
| 互斥路径合并 | 支持 | 来自已选择路径的实际激活即可进入，不等未选前驱 |
| 通过分支返回先前节点 | 支持 | 新激活，不复用旧完成状态 |
| 普通节点同时连接多条成功边 | 暂拒绝 | 这是实际分叉，单工作线程也不会使它变成互斥 |
| 同一 sourceHandle 连接多个目标 | 暂拒绝 | 一个出口实际触发多个分支 |
| AND 汇聚、交叉或无法证明互斥的合并 | 暂拒绝 | 需要批次、分支身份及明确汇聚语义 |
| 原无环并行图 | 保留旧路径 | P0 的 parallel-fork 样例在原并行引擎中验证 |

不能仅凭“入度大于一”认定是 AND 汇聚。P2 应沿互斥出口及错误/正常出口的控制关系验证合并；无法证明首批语义时拒绝并说明原因。循环允许后仍检查开始结束、端口、可达性与预算，队列耗尽而未到有效 END 不能算成功。
