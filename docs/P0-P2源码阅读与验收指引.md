# P0～P2 源码阅读与验收指引

更新日期：2026-10-26。适用范围：本仓库 Java 引擎的“保留原 DSL、复用原节点执行器”改造。

本文用于检查当前成果，按照“先看运行样例 → 跟踪关键源码 → 对照测试断言 → 执行验收命令”的顺序阅读。阶段任务以[实施计划](原引擎最小改造实施计划.md)为准；细节证据分别保存在 [P0 记录](P0兼容性基线与验收记录.md)、[P1 记录](P1原执行器复用与激活隔离验收记录.md)、[P2 记录](P2原DSL有环执行与分支路由验收记录.md)。

## 1. 目前完成了哪些任务

| 阶段 | 已完成工作 | 你应当能从源码和测试确认什么 |
| --- | --- | --- |
| P0：兼容性基线 | 核实原 DSL、节点注册、分支配置、重试、变量、模型历史和 SSE；固定 10 份原格式 JSON 和 48 项基线测试 | 明确原引擎已经有什么能力、哪些行为要保留，以及为什么不能只删除 DAG 检测 |
| P1：节点复用与隔离 | 直接调用原 NodeExecutor；区分每次激活与调用尝试；隔离输入、节点视图、变量、历史和回调；控制输出提交及迟到返回 | 同一业务执行器可以反复使用，但每次激活的状态和重试额度独立，超时旧调用不能覆盖新结果 |
| P2：分支与有环调度 | 补齐原格式 IF_ELSE；建立边索引和显式队列；允许分支回跳和互斥合并；令牌去重；加入激活数、时长和结构校验 | 原 LLM → 分支 → 返回原 LLM/走 END 的图可以执行，不要求改写成 LOOP/BACK |

当前已完成的是**原 DSL 的内部有环执行能力**。以下能力尚未在这条改造路径交付：

- P3：运行级 pause/resume、节点前断点、独立运行管理与事件接口。
- P4/P5：事务快照、跨进程恢复、执行中故障接管与外部副作用幂等处理。
- P6：有环并行分叉与 AND 汇聚。
- 后续入口整合：原 HTTP 控制器切换或显式选择增强路径。

P1 的变量快照、P2 的待执行队列是后续恢复的基础；目前没有保存到数据库，不能据此宣称服务重启后能够恢复。节点尝试被取消，也不等于运行级取消 API 已经交付。

## 4. P0 怎样验收：原行为有依据

### 4.1 看原协议与原限制

先看 [WorkflowDSL][dsl]、[Node][node]、[Edge][edge] 和[原格式样例目录][fixtures]。

确认图仍由 flowId、uuid、nodes、edges 构成；边仍使用 sourceNodeId、targetNodeId、sourceHandle。节点输入仍使用原 schema.value 的 literal/ref 形式。

再看 [WorkflowEngine][legacy-engine]：

- verifyWorkflow、hasCycle：旧路径存在无环约束。
- buildNodeExecuteChain：建立原静态前驱和后继关系。
- executeNode：旧节点状态参与跳过与前驱等待。
- executeNormalCondition / executeFailedCondition：旧成功与失败路径的解释。

这说明改造必须同时处理重复激活和调度状态，不能只放开 hasCycle；否则旧“执行过即跳过”和静态前驱等待假设仍在。

### 4.2 看兼容性测试

| 文件 | 重点核查 |
| --- | --- |
| [LegacyDslBaselineTest][baseline-dsl] | 原 JSON 经两种解析方式保留配置；顺序帧；原 DAG 并行汇聚；旧路径的能力边界 |
| [LegacyNodeBaselineTest][baseline-node] | START/END 展示对结果的改写；原 LLM 模板与历史；原插件、知识库参数与输出 |
| [LegacyRetryBaselineTest][baseline-retry] | maxRetries 是首次调用之外的追加次数；复用同一个旧 Node 会携带重试计数；超时与退避 |
| [LegacyVariablePoolBaselineTest][baseline-variable] | 原引用路径、缺失字段、null、字段增量写入和活动 Map 行为 |
| [LegacyControllerBaselineTest][baseline-controller] | 原入口、SSE 完成与异常处理契约 |

**P0 通过标准：**基线覆盖真实原执行器与原协议，而不是用新执行器模拟原功能。

注意历史时点：P0 核实当时只有 6 个原执行器，Java 缺少 IF_ELSE。P2 已补齐第 7 个执行器，当前注册测试相应验证“保留原 6 个并新增 IF_ELSE”。P0 文档中的“缺失”描述的是当时状态。

## 5. P1 怎样验收：复用执行器，又隔离每次执行

### 5.1 先分清四种身份

| 字段 | 表示什么 | 循环再次到达时 |
| --- | --- | --- |
| runId | 一次工作流运行 | 不变 |
| nodeId | 原图中的节点定义 | 不变 |
| activationId / executionId | 一次到达及其逻辑执行记录 | 新建；P2 使用控制令牌 ID 作为 activationId |
| attemptId / attemptNo | 一次激活内部的具体调用尝试 | 重试时新建；不新增业务激活 |

[NodeActivation][activation] 是对外可读取的执行快照；[NodeExecutionScope][scope] 保存内部执行过程。它们承担不同职责，不能只看原 Node.status 判断循环进度。

### 5.2 沿一次原节点调用向下跟踪

```text
NodeExecutionBridge.prepare
  复制原 Node 定义、解析并固定输入、记录来源、注册激活
NodeExecutionBridge.execute
  领取激活，查找原 NodeExecutor
AbstractNodeExecutor.execute
  沿用原重试次数、退避和错误策略
NodeExecutionScope.invoke
  创建私有 attempt、变量视图、受控回调和上下文
AbstractNodeExecutor.doExecute → 原业务 executeNode
  实际调用原 LLM / 插件 / 知识库逻辑
NodeExecutionScope.commit → WorkflowRunContext.complete
  验证仍有效，提交本次业务结果和被接受的历史
publishTerminals
  发布已接受的节点终态展示
```

重点检查这些条件：

- bridge 的注册表来自原 List<NodeExecutor>；原 [LLMNodeExecutor][llm]、[PluginNodeExecutor][plugin]、[KnowledgeBaseNodeExecutor][knowledge] 的业务方法仍在调用链里。
- NodeState 保留三参数构造方式；增强路径通过可选 execution 接入隔离。旧路径没有增强作用域时继续原流程。
- prepare 固定输入一次；重试使用私有副本。inputOrigins 记录生产者 executionId 和字段 present，区分缺失引用与显式 null。
- 每次激活和尝试使用独立 Node 视图；不向共享定义写回执行状态和重试次数。
- 本次尝试拿到的 VariablePool 不是运行的已提交池；节点内部写变量不能绕过统一提交。
- complete 对成功和原自定义错误输出整体替换最近输出，清除上轮多余字段；其他失败结果保存在执行记录中。
- 展示使用业务结果副本；START/END 回调不能破坏运行层保存的完整结果。
- 超时、取消或过期尝试不能更新已提交变量、模型历史和有效节点终态。
- 物理调用数在真实调用退出时递减；逻辑超时不会假装外部调用已经结束。

### 5.3 辅助文件按问题查阅

| 你要检查的问题 | 文件与方法 |
| --- | --- |
| 原输入引用是否另造了一套规则 | [NodeInputResolver][input-resolver]：resolve |
| 怎么整体替换输出且保留 null | [VariablePool][variable-pool]：snapshot、restore、replaceNodeOutputs、contains |
| 嵌套值和业务结果怎么脱离活动对象 | [JsonSnapshot][json-snapshot]：copy、mutable、result |
| 如何阻止迟到回调，如何应对满队列 | [WorkflowMsgCallback][callback]：guarded、produce；scope 的 gate / publishTerminals |
| 原模型历史是否仍支持开关和轮数 | [LlmChatHistory][history]；scope 的历史操作与 run-context 的 complete |
| 原业务代码怎样取得正确上下文 | scope.withContext、[EngineContextHolder][context-holder]，退出时恢复旧线程上下文 |

同一激活重试使用固定历史，不把失败尝试追加的对话自动喂给下一次尝试；这个增强路径约定与旧入口的直接执行行为要分开核查。详见 P1 验收记录。

## 6. P2 怎样验收：跟踪一次完整的有环执行

### 6.1 先运行主线测试，再调试

在 [WorkflowGraphExecutorTest][graph-test] 中运行：

```text
originalDslRunsThreeCyclesThroughTheOriginalLlmAndKeepsEveryExecution
```

测试使用 [branch-cycle.json][cycle-json]，输入 text=seed；[WorkflowGraphTestSupport][test-support] 中的模型客户端按顺序返回 RETRY、RETRY、PASS。调用的是原 LLMNodeExecutor，替换的是外部客户端。

预期轨迹如下：

| 步骤 | nodeId | 本节点 activationNo | 关键结果 |
| --- | --- | --- | --- |
| 1 | node-start::s | 1 | 发布 text=seed |
| 2 | spark-llm::generate | 1 | answer=RETRY |
| 3 | if-else::check | 1 | selectedHandle=branch_one_of::retry |
| 4 | spark-llm::generate | 2 | answer=RETRY，新的 executionId |
| 5 | if-else::check | 2 | selectedHandle=branch_one_of::retry |
| 6 | spark-llm::generate | 3 | answer=PASS，新的 executionId |
| 7 | if-else::check | 3 | selectedHandle=branch_one_of::pass |
| 8 | node-end::e | 1 | content=Result: PASS，运行成功 |

**必须核对的最终值：**

- run.status() 为 SUCCEEDED，run.outputs().get("content") 为 Result: PASS。
- run.getContext().executions() 共 8 份记录，LLM 和 IF_ELSE 各 3 份。
- LLM 三次 nodeId 相同、executionId 不同、activationNo 为 1/2/3。
- 每次分支 inputOrigins 中 actual 的生产者 executionId 对应本轮 LLM。
- 原 LLM 的 execute 被调用 3 次；原定义对象的 status 没有被增强运行写回。
- 成功时 pending 为空、无 READY/RUNNING 激活、physicalAttempts 为 0。

三次 LLM 激活对应两次回边，不能把“激活三次”误读成“回边三次”。该样例每次业务输入仍来自 START.text；历史开启时会带上已接受的对话，不依赖读取尚未产生的自身输出。

### 6.2 推荐 IDE 断点

| 断点位置 | 观察什么 |
| --- | --- |
| WorkflowGraphCompiler.compile | 输入是否仍是原 DSL；是否只校验可达性和支持结构，没有 DAG 禁环 |
| WorkflowGraphExecutor.tick 中取得 token 后 | token.id、targetNodeId、sourceExecutionId、edgeIndex |
| NodeExecutionBridge.prepare | activationId 是否等于 token.id；本节点下一激活序号和固定输入 |
| NodeExecutionScope.withContext | 实际进入原执行器时的 flowId/chatId、私有变量和执行身份 |
| IfElseNodeExecutor.executeNode / matches | actual、expected、case 顺序与 selectedHandle |
| WorkflowRunContext.complete | 提交前后的最近节点输出，以及 lastExecutions |
| WorkflowGraphExecutor.route | 成功/失败/条件出口怎样选择原 Edge，回边是否 issue 新令牌 |
| WorkflowGraphRun.finishIfIdle | endReached、队列、未决激活、物理调用数是否同时满足成功要求 |

调试器长时间暂停也会消耗墙钟预算。主线测试工具默认总时长为 5 秒；需要长时间单步时，仅在本地调试副本为该次调用传较大的 WorkflowExecutionLimits，验收运行仍使用原测试配置。不要把单步造成的超时误判成调度故障。

### 6.3 分支、合并、保护分别看哪里

| 问题 | 重点源码 | 验收依据 |
| --- | --- | --- |
| 分支怎样决定继续或退出 | IfElseNodeExecutor.definition / matches / operand；[ConditionValues][condition-values] | 原 cases 顺序，首个匹配，最后默认，and/or 短路；未匹配为正常业务结果 |
| 分支结果怎样找到边 | [NodeRunResult][node-result].selectedHandle；graph-executor.route | case ID 与 sourceHandle 精确匹配；不虚构出口 |
| 为什么同一节点能再次执行 | graph-run.issue → next；bridge.prepare | 回边创建新令牌，新激活不受原节点“执行过”状态限制 |
| 为什么重复投递不会重复调用 | graph-run.replay / next；bridge 的激活去重 | 同一令牌只消费一次；不同回边令牌仍正常激活 |
| 为什么合并不等另一条分支 | graph-executor 的队列推进方式 | 只消费实际到达的令牌，未选中分支不执行、不等待 |
| 怎样防止无限运行 | [WorkflowExecutionLimits][limits]；graph-executor.tick / checkDuration；scope 有效性检查 | 新激活创建前检查计数；总截止时间约束排队、重试和结果接受 |
| 为什么不会静默串行执行并行图 | compiler.compile | 普通成功分叉、同一 case 多目标等在执行前拒绝 |
| 为什么队列空不直接成功 | graph-run.finishIfIdle | 未到 END 且无剩余工作时 FAILED，错误为控制流停滞 |

普通成功边保留空 handle / normal_one_of 解释，失败边保留 intent_chain 解释；ERR_CODE_MSG 自定义输出走正常路径，ERR_FAIL_CONDITION 走失败路径。分支类型错误、输入不可用与“条件为 false”必须区分。

## 8. 如何运行验收

### 8.1 环境与证据边界

从仓库根目录执行，使用 Java 21 和 Maven。上述单元/契约测试不要求真实模型、插件服务、知识库或业务数据库；依赖首次下载或本地缓存仍需具备。

外部客户端使用替身，原节点执行器和增强调度链是真实代码；部分边界测试会专门注入阻塞/失败执行器或可控时钟。[WorkflowGraphTestSupport][test-support] 是测试装配器，不是生产入口。

### 8.2 先运行一个主线用例

```powershell
mvn -B -f core-workflow-java/pom.xml '-Dtest=WorkflowGraphExecutorTest#originalDslRunsThreeCyclesThroughTheOriginalLlmAndKeepsEveryExecution' test
```

需要看内部值时，在 IDE 直接运行同一个 JUnit 方法。

### 8.3 分阶段执行

P0 的五个基线测试类，当前合计 48 项：

```powershell
mvn -B -f core-workflow-java/pom.xml '-Dtest=Legacy*BaselineTest' test
```

P1 的四个测试类，合计 28 项：

```powershell
mvn -B -f core-workflow-java/pom.xml '-Dtest=NodeExecutionBridgeTest,NodeExecutionIsolationTest,OriginalExecutorBridgeTest,VariablePoolSnapshotTest' test
```

P2 的四个测试类，合计 106 项：

```powershell
mvn -B -f core-workflow-java/pom.xml '-Dtest=IfElseNodeExecutorTest,WorkflowGraphCompilerTest,WorkflowGraphExecutorTest,WorkflowGraphBudgetTest' test
```

参数化用例按每组输入分别计数，测试项数不等于 Java 方法数量。上面三组只运行阶段新增测试；完整回归仍需下一步。

### 8.4 最后做全量测试与打包

按仓库已有脚本执行：

```bash
./scripts/restart-java-workflow.sh --verify-only
```

Windows PowerShell 可使用 Git Bash：

```powershell
& 'C:/Program Files/Git/bin/bash.exe' ./scripts/restart-java-workflow.sh --verify-only
```

本机此前使用已有离线缓存与工作区临时目录，复现时可临时设置 MAVEN_ARGS：

```powershell
$p02PreviousMavenArgs = $env:MAVEN_ARGS
try {
    New-Item -ItemType Directory -Force -Path .local/p0-temp | Out-Null
    $env:MAVEN_ARGS = '-o -s C:/Users/Administrator/.m2/settings.xml -Dmaven.repo.local=C:/Users/Administrator/.m2/repository -DargLine=-Djava.io.tmpdir=E:/Sheepxj/Code/PaiFlow-main/.local/p0-temp'
    & 'C:/Program Files/Git/bin/bash.exe' ./scripts/restart-java-workflow.sh --verify-only
    if ($LASTEXITCODE -ne 0) {
        throw 'Java workflow verification failed'
    }
} finally {
    $env:MAVEN_ARGS = $p02PreviousMavenArgs
}
```

这组本机路径无需迁入项目配置；在其他机器上使用自己的 Maven 设置、缓存和临时目录。运行前确认 JDK 为 21。

--verify-only 只执行 Maven verify，包括测试和打包。脚本默认模式还会构建和重启 Java 容器，审查阶段可以先使用 --verify-only；需要容器验证时另在 Docker 可用环境执行默认模式。

### 8.5 怎样检查结果

| 证据位置 | 怎么判断 |
| --- | --- |
| Maven 控制台 | Tests run、Failures、Errors、Skipped 和最终 BUILD SUCCESS；不能只看生成了 JAR |
| core-workflow-java/target/surefire-reports/ | 查看每类 TEST-*.xml 与文本报告，确认具体用例及失败堆栈 |
| core-workflow-java/target/workflow-java.jar | 确认打包成功；它本身不证明业务执行正确 |
| .local/p2-final-verify.log | 本机上次 P2 全量验证日志，属于本地生成文件 |
| 三份阶段验收文档 | 历史测试数量、行为约定和未验证边界 |

## 9. 人工检查清单

建议逐项勾选并记录问题，再决定是否进入 P3：

- [ ] 确认旧 HTTP、本次增强入口、历史 V2 的关系，没有把不同路径的能力混为一谈。
- [ ] 读过原格式 branch-cycle.json，能解释每个条件输入 ID、case 和 sourceHandle。
- [ ] 调试过三轮生成测试，观察到同一 nodeId 的不同 executionId，以及两次回边。
- [ ] 能从 bridge 跟进原 LLM/插件/知识库执行器，确认没有另写一套业务实现。
- [ ] 能区分节点定义、激活和尝试，并确认新一轮激活与同轮重试使用不同计数规则。
- [ ] 核查固定输入、提交前私有输出、整体替换和缺失字段的断言。
- [ ] 核查分支首个匹配、默认出口、短路及类型错误，理解 false 不等于执行失败。
- [ ] 核查互斥合并、令牌去重和并发 tick 不重复派发。
- [ ] 核查无出口结构、无限业务循环和空队列停滞的不同错误边界。
- [ ] 核查超时迟到、历史隔离、终态缓冲、物理调用数与成功收敛。
- [ ] 原 DAG 并行继续通过；增强路径对不支持的并行结构执行前明确拒绝。
- [ ] 分阶段测试和完整 verify 通过，阅读实际报告，而非只依赖文档中的历史数字。
- [ ] 接受当前未交付暂停/恢复/持久化的范围；相关检查留给 P3～P5。

记录反馈时建议使用“文件与方法 → 触发场景 → 当前结果 → 预期结果 → 对应测试”的格式。这样可以直接补测试并修复具体行为，避免把源码阅读问题和后续阶段需求混在一起。
