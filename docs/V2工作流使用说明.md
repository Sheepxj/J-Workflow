# V2 工作流使用说明

当前 V2 提供独立的运行 API，旧工作流与原 SSE 接口保持原路径。V2 入口只接受 `dslVersion: "2"`，校验失败不会自动降级。

当前实现包含结构化循环、多次节点执行、单次调用重试、事件查询、暂停/继续和节点前断点。默认使用内存存储，进程退出后运行数据会丢失；启用 JDBC 存储后可以保存断点并恢复。

## 运行示例

请求示例为 `core-workflow-java/examples/structured-loop.json`，包含 `definition` 和 `inputs`。使用 MOCK 节点运行三轮“生成—校验”，最后输出 `draft-3`。

服务地址通过环境变量设置，不固定绑定部署地址。以下使用 PowerShell：

```powershell
$workflowBaseUrl = $env:WORKFLOW_BASE_URL
$requestPath = 'core-workflow-java/examples/structured-loop.json'
$requestBody = Get-Content -LiteralPath $requestPath -Raw -Encoding utf8
$started = Invoke-RestMethod -Method Post -Uri "$workflowBaseUrl/api/workflow/v2/runs" -ContentType 'application/json; charset=utf-8' -Body ([Text.Encoding]::UTF8.GetBytes($requestBody))
$runId = $started.runId
Invoke-RestMethod -Uri "$workflowBaseUrl/api/workflow/v2/runs/$runId"
```

启动返回 HTTP 202 和 runId，不阻塞等待流程结束。查询最终状态应为 `SUCCEEDED`，`outputs.result` 为 `draft-3`；`executions` 中每轮生成、校验分别保留独立记录。

## 控制与事件

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/workflow/v2/runs` | 创建运行，正文为 definition 和 inputs |
| GET | `/api/workflow/v2/runs/{runId}` | 查询运行、执行历史及输出 |
| GET | `/api/workflow/v2/runs/{runId}/events?after=0&limit=100` | 按运行内事件序号增量查询，limit 范围为 1～1000 |
| POST | `/api/workflow/v2/runs/{runId}/pause` | 请求暂停，返回 202 不代表已进入 PAUSED |
| POST | `/api/workflow/v2/runs/{runId}/resume` | 从 PAUSED 继续；RUNNING 状态下重复调用幂等 |
| POST | `/api/workflow/v2/runs/{runId}/cancel` | 取消运行，协作通知活动调用，不保证外部副作用撤销 |
| POST | `/api/workflow/v2/runs/{runId}/executions/{executionId}/resolve` | 处理重启后结果未知的调用，正文为 action（RETRY 或 COMPLETE）及 outputs |

在节点定义上配置 `breakpoint: true`，每次到达该节点时先暂停，继续后才执行本次激活。下一轮到达同一节点时会再次暂停。

暂停采用 `RUNNING → PAUSING → PAUSED`：停止派发后继，等待当前调用收敛并提交结果。查询到 PAUSED 后再继续。对 PAUSING 调用 resume 返回 409，避免把尚未确认的暂停当成已保存断点。

当前总时长按运行开始后的墙钟时长计算，暂停时间也计入；长时间等待需求应设置适当预算，后续可扩展计时策略。

## 持久化断点与恢复

在 Java 服务配置中启用：

```yaml
workflow:
  v2:
    enabled: true
    store: jdbc
    initialize-schema: false
```

使用 Java 服务已有的主 DataSource。先在对应 Java 数据库执行 `core-workflow-java/src/main/resources/db/workflow-v2.sql` 创建独立的 `workflow_v2_run` 表；开发环境也可以设置 initialize-schema 为 true 自动创建。不要在 Python 基线数据库执行该脚本。

状态、已提交输出、待消费令牌、待派发尝试、重试时间、作用域和事件历史保存在同一个事务快照中。数据库行锁与 revision 保护状态转移；运行租约防止多个调度器同时推进。租约时长为 30 秒，非正常退出后接管需要等待原租约到期。已确认暂停的运行释放租约，重启后仍保持 PAUSED，收到 resume 才推进。

恢复按三类处理：

1. 已提交成功结果：保留原 executionId 和输出，不再次执行。
2. READY 待派发任务：从持久化任务记录继续，不额外消耗重试次数。
3. RUNNING 但没有提交结果的调用：记录 INTERRUPTED。安全节点默认在剩余尝试预算内重试；LLM/PLUGIN 默认转为 RECOVERY_REQUIRED 并暂停，避免重复副作用。

config.recovery 可显式设置 RETRY 或 MANUAL。只有确认外部服务可安全重试时才设置 RETRY；引擎不保证外部业务恰好一次。

人工处理未知结果时，可提交 `{"action":"COMPLETE","outputs":{...}}` 填入经业务核实的输出，再 resume；或者在仍有 maxAttempts 预算时提交 `{"action":"RETRY"}` 后 resume。每次重试仍保留原 executionId，使用新的 attemptId。直接 resume 一个存在 RECOVERY_REQUIRED 的运行会返回 409。

当前数据库自动化验证使用 H2 MySQL 模式，覆盖事务回滚、关闭重开数据库、更换调度器、租约保护及旧结果过滤；尚未在真实 MySQL 容器中完成部署重启验证。

事件保留 nodeId 并包含 executionId、attemptId、scopeId、iterationNo 和 sequence。展示历史时应以 executionId 区分执行，以 attemptId 区分失败重试的流式内容。

## 节点和配置

- START：默认输出运行输入。
- END：根据 inputBindings 收集最终输出。
- LOOP：内置循环控制，按循环定义决定 body/exit。
- XOR 或 `routing: EXCLUSIVE`：条件选择一条出边，要求默认边；多匹配时报错。
- MOCK：config.operation 支持 ECHO、GENERATE、VALIDATE、CONSTANT。VALIDATE 使用 passesOnIteration；failAttempts 用于确定性重试验证。
- LLM：注册现有 ModelServiceClient 时可用；config 沿用模型请求的 modelId、model、url、apiKey 等字段，template 使用固定输入替换，systemMsg 为系统提示。默认输出 text、reasoning、usage；outputMode 为 JSON 时将响应解析成对象，便于条件路由。不会使用旧执行器的隐式全局聊天历史。
- PLUGIN：注册现有 PluginServiceClient 时可用；config 使用现有 pluginId、operationId、appId 等工具配置。只调用一次底层服务，不重复应用旧执行器的重试或回调。

LLM/PLUGIN 的真实外部服务需要现有工程配置。本地自动测试使用替身验证调用边界，不调用付费服务。外部工具是否支持幂等由对应集成实现决定，当前适配不承诺恰好一次副作用。

当前不支持嵌套循环或并行分叉/汇聚，编译器明确拒绝这些结构。可通过 `workflow.v2.enabled=false` 关闭 V2 API 和新运行服务。
