# P1 原执行器复用与激活隔离验收记录

日期：2026-10-25。对应 [原引擎最小改造实施计划](原引擎最小改造实施计划.md) 的 P1。状态：已完成验收，P2 尚未开始。

本阶段交付原节点执行器的桥接和隔离机制。它接受原 Node 定义，调用现有 NodeExecutor；不引入新的工作流 DSL，不重写 LLM、插件或知识库业务方法。原控制器的执行路径、DAG 校验及实验 V2 保持原状。

## 1. 实现入口与阅读顺序

主要新增代码位于 `core-workflow-java/src/main/java/com/iflytek/astron/workflow/engine/execution/`。

| 文件 | 关键方法或对象 | 作用 |
| --- | --- | --- |
| [NodeExecutionBridge][bridge] | prepare、execute | Spring 注入原 NodeExecutor 列表，按原节点类型查找并调用；准备、执行一次激活 |
| [WorkflowRunContext][run] | variables、execution、executions、complete | 管理本次运行的已提交变量、执行历史和模型历史，集中发布结果 |

## 2. 如何调用原节点

NodeExecutionBridge 已作为 Spring 组件注册，使用现有 `List<NodeExecutor>`，不使用 V2 的 NodeTaskExecutor。其内部注册表是 `Map<NodeTypeEnum, NodeExecutor>`。

P2 的控制流调度器可以注入该组件。当前也可在 Java 内直接创建，用固定的原节点定义执行一次激活：

```java
NodeExecutionBridge bridge = new NodeExecutionBridge(registeredExecutors);
VariablePool initial = new VariablePool();
initial.replaceNodeOutputs(startNode.getId(), inputs);
WorkflowRunContext run = new WorkflowRunContext(runId, flowId, chatId, initial, workflowCallback);

NodeActivation started = bridge.execute(run, startNode);
NodeActivation worked = bridge.execute(run, workNode);
```

registeredExecutors、节点、输入和父回调由调用方提供。示例是内部调用方式，不是新增 HTTP 协议，也没有自动遍历图。

如需先准备后执行，可以使用 `prepare(run, activationId, definition)`，再以返回的 executionId 调用 execute。同一 executionId 重复执行不会重复调用业务节点；复用同一 activationId 时保留原准备结果，不更新已固定的定义和输入。不同目标节点不能复用同一 activationId。

第一批运行上下文只允许一个未取消的逻辑激活同时执行。已经超时或取消的物理调用可能仍在返回途中，physicalAttempts 单独计数；它不会因为逻辑状态结束而提前清零。

## 3. 一次激活与一次尝试

```text
prepare：
  复制原 NodeData，保留原 nodeId
  读取已提交变量，调用原输入解析
  固定输入、来源和本次可见的对话历史
  创建 executionId，记录 activationId 与节点激活序号

execute：
  领取 READY 激活
  调用原 NodeExecutor.execute(NodeState)
    原 AbstractNodeExecutor 管理 maxRetries、退避和错误策略
    每次调用尝试创建独立 attemptId、节点视图、变量视图与回调视图
    安装 flowId/chatId/sid/执行身份，调用原 executeNode 业务方法
    返回或超时后关闭该尝试的发布权限
  发布已确认业务结果、变量及历史
  发送已经接受的终态展示事件
```

记录中有三类身份：

- nodeId 仍是原定义 ID，例如 spark-llm::generate，类型识别、原引用和业务历史键保持原含义。
- executionId 标识一次业务激活；同一节点激活三次产生三份记录。
- attemptId 标识本次激活的一次调用尝试；maxRetries 为 2 时最多调用三次，不新增业务激活。

Node 的定义对象不承载这些新执行状态。每次激活和尝试都持有复制后的 NodeData，重试计数不写回共享定义。原 NodeState 三参数构造方式仍存在，增强执行使用可选的第四个 execution 参数。

## 4. 输入、来源和输出提交

### 固定输入

桥接器在准备激活时解析原输入一次。后续尝试使用该快照的私有副本，即使第一次尝试修改传入 Map、自己的变量视图，下一次尝试也仍使用原输入。

inputOrigins 保存来源种类、原节点和路径、已提交生产者 executionId，以及 present 标志。因而以下两种输入虽然业务值都为 null，仍可以区分：

- 引用字段不存在：NODE_OUTPUT，present=false。
- 字面量 null 或引用到已存在的 null 字段：present=true。

本阶段保持原缺失直接引用透传 null 的行为，不提前实施 P2 的条件节点输入校验。来源记录为后续校验提供依据。数组路径的存在性判断遵循原读取语法，不偷偷改变旧 `items[0]` 这类路径的解释。

### 变量视图与快照

原执行器仍可使用 NodeState.variablePool，但它是本次尝试的独立副本，不能直接改动运行的已提交变量。桥接层采用最终业务 NodeRunResult 发布本次输出。

VariablePool 新增操作：

| 方法 | 语义 |
| --- | --- |
| snapshot() | 返回与活动变量分离的 JSON 值快照，嵌套 Map/List 不可修改 |
| restore(snapshot) | 先验证并复制，再替换整份变量，输入非法时不部分覆盖 |
| replaceNodeOutputs(nodeId, outputs) | 整体替换节点输出，清除上次独有字段，保留显式 null |
| contains(nodeId, path) | 按原路径读取语法判断字段是否存在 |

快照采用 JSON 值语义，任意 Java 对象类型不作为持久化类型保证；未声明类型的数值经 JSON 转换后可能成为不同 Number 子类。P0 对数值比较的要求仍适用。

旧 set/get 的字段级写入、直接 null 写入行为和活动 Map 返回方式保持原契约；增强运行不把内部已提交池暴露给节点。成功结果和 ERR_CODE_MSG 的自定义输出会发布；失败分支结果留在执行记录中，不伪装成成功输出。

## 5. 回调、超时与迟到返回

增强执行中的成功及错误展示使用结果副本。START 回调仍可隐藏展示输出，END 回调仍可展示输入并生成答案，但这些操作不会改变供运行层保存的业务结果。

终态事件先保存在当前尝试中：

- 下一次重试开始前，发送已确认失败尝试的展示事件。
- 最终激活结果提交后，发送最后一次已接受的终态事件。
- 超时会清除该尝试可能尚未接受的终态内容，记录超时结果。
- 取消或迟到尝试的输出与回调不能发布到当前运行。

开始与流式片段可以在有效尝试执行期间发送。受控回调使用现有父消费者，保留原 stream 载荷形式；节点不能通过本次回调视图结束整个工作流或关闭父消费者。

对于“第一次超时、第二次成功、第一次最后才返回”的情况：第一份私有变量与输入不会再被读取，它的流片段与成功通知被拒绝，第二次结果保持不变。旧物理调用仍可能执行外部操作，P1 不承诺撤销外部副作用。

当流队列背压阻塞生产者时，尝试有效性也会参与父队列的生产检查。向消费者发送事件不持有运行状态锁；取消与结果提交只使用状态临界区。因此消费者读取运行状态不会与满队列的生产者互相等待，取消也能使受控生产者退出。已在有效期间接受的流式片段可能因传输缓冲较晚到达，不代表节点仍然有效。

## 6. 上下文与原模型历史

每次业务尝试安装独立 EngineContext，保持原 flowId、chatId、nodeId，附带 execution 身份、受控回调及当前执行作用域。正常、异常或迟到返回时都恢复原线程上下文，不修改调用方原有上下文对象。

LlmChatHistory 的原接口仍供原 LLMNodeExecutor 使用。当线程没有增强作用域时，继续使用原缓存行为；存在作用域时，读写落入本次尝试的私有历史。

增强运行在创建时捕获原 chatId 的会话历史，随后每次激活从本运行已提交历史读取。被接受的历史才写回运行和原会话缓存。相同 chatId 的并行独立运行也不会中途反读另一运行刚提交的历史；会话缓存仍由最近提交者更新。

原历史功能保留：启用开关、轮数限制、系统和用户消息，以及关闭读取历史时仍收集本次对话的行为。增强路径有一个明确差异：同次激活的重试使用固定历史，不把失败或超时尝试新追加的消息反馈给下一次尝试；迟到 LLM 响应也不能追加历史。这个差异有专门测试，旧入口行为未改变。

当前支持导出独立变量与历史快照，但没有将 WorkflowRunContext 整体保存到数据库。持久化 DTO、事务及重启恢复仍属于 P4/P5。

## 9. 下一阶段的接口边界

P2 可以在控制令牌到达节点时调用 prepare/execute，并使用执行结果的原状态和分支出口决定后继。节点多次执行不再需要清空全图 Node.status，也不需要替换现有业务执行器。

P1 尚未提供新的图调度、IF_ELSE 执行器、工作流暂停 API、JDBC 快照或服务重启恢复。因此旧 HTTP 路径仍按旧引擎运行，不能把本阶段完成解读为原格式工作流已经可以带环执行。
